# Phase 0 security preparation — 15 October 2026

Scope: the 15 October read-only 2FA audit, independently rechecked against project `igrddscmrdrrwtvyspbf`, and the existing weekly branch. No hosted SQL, functions, Auth configuration, account data, or email delivery were modified. No TOTP UI, MFA enforcement, recovery flows, session revocation, or new security-email service is implemented. The optimized roll function is byte-for-byte unchanged from both the weekly baseline and audited main `8ebca9b`.

## Changes

1. Add `public.public_player_directory`, a deliberately owner-executed, security-barrier view exposing **only `id` and `username`** to authenticated users. Its cross-player visibility is intentional; an invoker view would inherit own-row RLS and break discovery. Never extend it with `SELECT *`, balances, equipment state, timestamps, hidden status, or lease fields. No anonymous directory access is granted.
2. Move DM search, conversation/realtime name resolution, cheque-recipient search, and `loadUsername` to that projection. Full `players` reads retain the existing owner policy after the broad `Authenticated users can read player usernames` policy is dropped. Existing `get_public_profile`, chat-profile and leaderboard RPCs continue to expose their explicit public fields; their contracts and leaderboard-hidden filtering are preserved. Public profile statistics already intentionally include total rolls, lifetime earnings, inventory capacity, showcase and best gem. This change does not make those existing public statistics private. Lifetime counts continue to use `total_rolls`.
3. Revoke direct private-message INSERT and broad UPDATE. Only recipients may update `read_at`; attempts to change content, sender, recipient, ID or creation time fail at the column privilege boundary. Table-level and independent column-level grants are removed. Send/read APIs and realtime INSERT subscriptions remain the same.
4. Keep the deployed `send_private_message` validation, returned row, five-second cooldown, and existing moderation trigger. Add a per-sender transaction advisory lock before reading the last message, so concurrent requests cannot both pass. This does not lock the player gameplay row. Use wall-clock time for checking and assigning `created_at`, including after a lock wait; lock release is automatic on commit/rollback. Pin its search path to empty and qualify its row return type. No moderation trigger or message constraints are replaced.
5. Remove unnecessary client `TRUNCATE`, `REFERENCES` and `TRIGGER` privileges on players and messages, and all client privileges on `admins`/`admin_viewers`, including independent column grants. TRUNCATE bypasses RLS. Service-role access is retained. Revoke PUBLIC/anonymous execution of three membership-guarded catalog admin RPCs, retaining authenticated/service execution and their existing role checks.
6. Remove full claims/context/debug logging from the canonical admin function and its legacy panel copy. Existing administrative mutation audit records remain. Pin the browser SDK to `2.117.3`, the version served by the existing floating `@2` URL during this review. Pin these two admin imports to `@supabase/server@1.9.2`, the current resolution of the prior floating import. Other functions and the roll import are deliberately untouched; this is not a project-wide transitive dependency lock.

## Admin authorization decision

The live admin v54 function uses owner-only writes; live `admins` has one member, matching that owner. The repository already has `adminAccess` owner/editor/viewer logic, an explicit SixSeven67 editor migration, and editor tests. The user confirmed **preserve repository roles** during this implementation. Phase 0 does not seed, remove, promote, or demote accounts and does not replace the existing membership model with an owner-only model.

Deploying the repository's admin function includes that pre-existing owner/editor/viewer implementation: owner/bootstrap and members of `admins` can write; `admin_viewers` have the existing restricted read actions. The three catalog RPCs already require `admins` membership. The owner bootstrap exception in the Edge Function remains; catalog RPCs require actual membership, so keep the owner's existing row. Event managers retain their separate intentional event permission. Viewer access to reporting RPCs still depends on the existing reporting migrations; do not broaden all admin RPCs to viewers.

The relevant live review found membership RLS enabled with no browser policies, no public view exposing players, no public-schema function writing admin membership, and no player-reading invoker RPC available to normal clients (the identified invoker helpers are service-only). Reviewed administrative RPCs use trusted membership/owner checks or guards; service-only `admin_adjust_economy_cash` accepts an admin parameter but is not client-executable. Avatar metadata is used for display, not privilege decisions. These are bounded checks, not a claim that every one of the 614 RPCs is fully security-audited.

## Manual rollout — owner only

Do not bulk-deploy the weekly branch: it also includes unrelated, unfinished release-disabled Christmas work.

1. Review/test in staging first, using the current hosted schema and existing migrations. Verify `players`/`private_messages` still have RLS enabled and the existing own-row/participant read policies. Check for new permissive policies or changed grants since this review. Verify `admins`/`admin_viewers` exist; do not change membership during this rollout.
2. Apply **only `20261015034907_phase_zero_security_preparation.sql`** first. This adds the identity directory and explicitly grants Data API access. Confirm authenticated directory search works and contains exactly two columns. The old broad players access intentionally remains until step 4.
3. Publish the frontend changes. Verify DM/cheque search, conversation names and public username resolution use the directory. Invalidate caches and ask players with older open tabs to refresh; old callers querying `players` will see only their own identity after step 4.
4. Apply **only `20261015035054_phase_zero_access_boundaries.sql`**. This closes the vulnerabilities and installs the serialized send function. Each migration is transactional and tested for reapplication. Check PostgREST schema reload completion.
5. Deploy **only canonical `supabase/functions/admin/index.ts`** as `admin`, retaining the live **`verify_jwt=true`** gateway setting. Deploy from the repository root, not the legacy panel directory. This includes the repository's pre-existing editor/viewer behavior described above. Do not deploy `roll` or unrelated functions for Phase 0.
6. With two ordinary test accounts, confirm A can read its own full state and cannot read B's money/equipment/lease fields; directory/profile/leaderboard results still work. Send A→B, verify moderation/read receipt/unread badge/realtime delivery, reject direct INSERT and content/sender/time edits, and confirm back-to-back/concurrent sends are throttled. Confirm a third account cannot read the conversation. Verify wallet/inventory/gameplay and owner/editor/viewer panel access. Check new function logs contain no claims dumps; old retained log entries are not removed by this patch.
7. Rerun the hosted security advisor after deployment. Handle the manual Auth/SMTP checklist above separately. Do not switch on mandatory MFA, build recovery flows, or shorten session policies under this release.

If a migration fails, its transaction rolls back; resolve the schema mismatch before retrying. Prefer fixing forward. The directory is additive and can remain. After the restriction migration, roll back the frontend only to a build retaining the directory readers; restoring the broad read policy or direct message INSERT/UPDATE would reopen the vulnerabilities. There is intentionally no unsafe rollback migration. Already altered historical message content cannot be detected or repaired by this patch.
